# Полная документация по коду проекта Alliance

Дата подготовки: 10.06.2026

## 1. Назначение проекта

Alliance - веб-приложение на Django для управления задачами, работниками и командами. Система разделяет пользователей на менеджеров и работников, позволяет создавать задачи, назначать их отдельным работникам или командам, учитывать рейтинг, навыки, рабочее время и формировать рекомендации по исполнителям.

Основные возможности:

- регистрация пользователей с ролями `worker` и `manager`;
- разграничение интерфейсов менеджера и работника;
- создание, редактирование, удаление и закрытие задач;
- назначение задач работнику или команде;
- ведение команд, состава команд и заметок менеджера;
- учет навыков работников;
- расчет рейтинга по результатам задач;
- учет рабочего времени работников через таймер;
- рекомендации работников и команд для задач;
- рекомендации состава команды;
- пересчет метрик работников и команд по истории задач;
- HTML-интерфейс с CSS/JS-активностями без отдельного frontend-фреймворка;
- набор Django-тестов для ключевой бизнес-логики.

## 2. Технологический стек

Backend:

- Python;
- Django;
- Django ORM;
- Django Templates;
- SQLite как локальная база данных;
- стандартные Django-сессии и CSRF-защита;
- Django TestCase для тестирования.

Frontend:

- HTML-шаблоны Django;
- CSS-файлы в `alliance/static/css`;
- JavaScript-файлы в `alliance/static/js`;
- модальные окна, фильтры, таймер рабочего времени и подбор исполнителей реализованы обычным JavaScript.

Хранение данных:

- `db.sqlite3` в каталоге `alliance`;
- миграции находятся в `accounts/migrations` и `tasks/migrations`;
- в документации миграции рассматриваются как служебный слой схемы, а не основной функциональный код.

## 3. Общая архитектура

Проект построен как классический Django-монолит с архитектурой MVT:

- `models.py` описывает данные и инварианты;
- `forms.py` отвечает за ввод, валидацию и подготовку данных из форм;
- `views` обрабатывают HTTP-запросы, права доступа, фильтрацию и сбор контекста;
- `templates` формируют HTML;
- `services` содержат бизнес-логику, которую важно тестировать отдельно от представлений;
- `static/js` добавляет интерактивность;
- `static/css` оформляет интерфейсы менеджера и работника.

Ключевая особенность проекта - часть логики вынесена из views в сервисы:

- расчет рекомендаций;
- расчет состава команды;
- закрытие задач;
- пересчет метрик;
- учет рабочего времени;
- расчет рейтинга.

Это делает проект удобнее для тестирования и развития: view отвечает за HTTP-сценарий, а сервис - за правило предметной области.

## 5. Конфигурация Django

Файл: `alliance/alliance/settings.py`

Назначение:

- задает базовые настройки Django;
- подключает приложения `accounts` и `tasks`;
- настраивает SQLite;
- настраивает шаблоны, статические файлы, язык и часовой пояс;
- подключает кастомную модель пользователя `accounts.User`;
- читает `.env` без сторонних библиотек.

Важные настройки:

```python
AUTH_USER_MODEL = 'accounts.User'
LANGUAGE_CODE = 'ru-ru'
TIME_ZONE = 'Europe/Moscow'
LOGIN_REDIRECT_URL = '/'
LOGOUT_REDIRECT_URL = '/accounts/login/'
LOGIN_URL = '/accounts/login/'
```

Переменные окружения:

- `DJANGO_SECRET_KEY` - секретный ключ Django;
- `DJANGO_DEBUG` - режим отладки;
- `DJANGO_ALLOWED_HOSTS` - список разрешенных хостов;
- `MANAGER_REGISTRATION_CODE` - код регистрации менеджера.

Функция `_load_dotenv()` ищет `.env` в корне репозитория и в папке `alliance`, затем переносит пары `KEY=VALUE` в `os.environ`.

## 6. Модель данных

### 6.1 Пользователи и аккаунты

Файл: `alliance/accounts/models.py`

#### `User`

Кастомная модель пользователя, наследуется от `AbstractUser`.

Основные поля:

- `role` - роль пользователя: `manager` или `worker`;
- `rating` - числовой рейтинг;
- `full_name`, `phone`, `address`, `website`, `github`, `twitter`, `telegram` - профильные данные;
- `specialization` - основной тип задач работника;
- `collaboration_score` - эффективность в команде от 1 до 10;
- `reliability_score` - надежность по индивидуальным задачам от 1 до 10;
- `solo_tasks_completed`, `solo_tasks_failed` - статистика индивидуальных задач;
- `team_tasks_completed`, `team_tasks_failed` - статистика командных задач;
- `velocity_score` - скорость и соблюдение сроков;
- `type_stats` - JSON-статистика по типам задач.

Методы:

- `team_names_display(limit=3)` - возвращает краткий список команд пользователя для UI;
- `shares_team_with(other)` - проверяет, состоит ли пользователь в одной команде с другим пользователем;
- `__str__()` - человекочитаемое отображение пользователя.

#### `Skill`

Справочник навыков.

Поля:

- `name` - название навыка;
- `skill_type` - `soft` или `hard`;
- `related_task_types` - связанные типы задач через запятую;
- `icon` - CSS-класс иконки.

#### `UserSkill`

Связь пользователя и навыка.

Поля:

- `user`;
- `skill`;
- `value` - оценка навыка от 1 до 10.

Ограничение:

- `unique_together = ('user', 'skill')`, то есть у одного пользователя не может быть двух оценок одного навыка.

#### `WorkSession`

Сессия рабочего времени работника.

Поля:

- `user` - работник;
- `started_at` - время старта;
- `ended_at` - время окончания.

Методы:

- `is_active` - активна ли сессия;
- `duration_seconds()` - длительность в секундах.

### 6.2 Задачи и команды

Файл: `alliance/tasks/models.py`

#### `Task`

Задача в системе.

Типы задач:

- `BD`;
- `Front`;
- `Backlog`;
- `Canceled`;
- `Design`;
- `DB`;
- `Back`.

Статусы:

- `open` - открыта;
- `in_progress` - в работе;
- `completed` - выполнена;
- `failed` - провалена.

Поля:

- `title` - название;
- `description` - описание;
- `link` - внешняя ссылка;
- `types` - JSON-список типов задач;
- `rank` - вес задачи в рейтинге;
- `due_date` - срок выполнения;
- `status` - статус;
- `assigned_to` - назначенный работник;
- `team` - назначенная команда;
- `created_by` - создатель;
- `created_at` - дата создания;
- `completed_by` - пользователь, закрывший задачу;
- `completed_at` - дата закрытия.

Инварианты:

- задача должна быть назначена либо работнику, либо команде;
- нельзя одновременно назначить задачу и работнику, и команде;
- у задачи должен быть хотя бы один валидный тип;
- дубликаты типов удаляются при валидации.

Методы:

- `is_overdue()` - проверка просрочки;
- `priority_label()` - UI-метка приоритета по `rank`;
- `status_ui_label()` - UI-метка статуса;
- `task_code` - код вида `TASK-0001`;
- `primary_type` - первый тип задачи.

#### `Team`

Команда работников.

Поля:

- `name` - название;
- `description` - описание;
- `manager_notes` - приватные заметки менеджера;
- `members` - участники команды;
- `target_types` - целевые типы задач;
- `synergy_score` - слаженность команды;
- `cohesion_score` - совместимость участников;
- `dominant_task_type` - доминирующий тип задач;
- `tasks_completed_count`, `tasks_failed_count` - статистика командных задач;
- `created_by` - создатель;
- `created_at` - дата создания.

Методы:

- `get_members()` - возвращает работников команды;
- `total_rating()` - суммарный рейтинг участников;
- `priority_label()` - приоритет команды по среднему рангу задач.

## 7. Роли и права доступа

В системе есть две основные роли:

- `manager` - управляет задачами, командами, работниками и навыками;
- `worker` - видит свои задачи, команды, профиль, рейтинг и таймер.

Файл: `alliance/tasks/decorators.py`

Декоратор `manager_required` проверяет, что пользователь авторизован и имеет роль менеджера. Если пользователь не менеджер, его перенаправляет на `dashboard`.

Права в профилях:

- менеджер может просматривать и редактировать профили работников;
- работник может просматривать собственный профиль;
- работник может просматривать профили коллег, если они состоят в общей команде;
- редактирование навыков доступно только менеджеру.

Права по задачам:

- работник может брать и закрывать задачи, назначенные ему лично;
- работник может работать с командной задачей, если состоит в назначенной команде;
- менеджер может создавать, редактировать, закрывать и удалять задачи.

## 9. Формы

### 9.1 Формы аккаунтов

Файл: `alliance/accounts/forms.py`

Расширяет `UserCreationForm`.

Особенности:

- поддерживает выбор роли;

Форма редактирования личных данных работника:

- имя;
- email;

- адрес;
- сайт;

- Twitter;

Динамическая форма навыков:

- создает поле под каждый `Skill`;
- начальное значение берется из `UserSkill`;

### 9.2 Формы задач и команд

Файл: `alliance/tasks/forms.py`

#### `TaskForm`

Форма создания и редактирования задачи.

Особенности:

- `types` представлен как `MultipleChoiceField`;

- можно назначить либо работника, либо команду;

#### `TeamForm`

Форма создания и редактирования команды.

Особенности:

- `target_types` выбираются чекбоксами;

## 10. Views приложения `accounts`

Файл: `alliance/accounts/views.py`

### `register(request)`

Регистрирует пользователя.

Логика:

Доступ:

## 11. Таймер рабочего времени

Сервис: `alliance/accounts/services/work_timer.py`

Views: `alliance/accounts/work_timer_views.py`

Назначение:

- работник может включить таймер при начале работы;
- таймер создает `WorkSession`;
- при остановке заполняется `ended_at`;
- менеджер видит сводку по активным, дневным и недельным сессиям работников.

Сервисные функции:

- `get_active_session(user)` - возвращает активную сессию;
- `start_session(user)` - создает сессию, если активной нет;
- `stop_session(user)` - закрывает активную сессию;
- `session_status_payload(user)` - формирует JSON-состояние;
- `format_duration(total_seconds)` - форматирует длительность как `HH:MM:SS`;
- `get_workers_work_summary()` - формирует сводку для менеджера.

HTTP endpoints:

- `work_timer_status`;
- `work_timer_start`;
- `work_timer_stop`;
- `work_timer_toggle`.

Особенности:

- endpoints доступны только работникам;
- неработник получает `403`;
- ответ возвращается в JSON;
- `toggle` сам определяет, нужно стартовать или остановить сессию.

Сигнал:

- `accounts/signals.py` содержит `stop_work_timer_on_logout`, который закрывает активную сессию при выходе пользователя.

### 12.2 Управление задачами

Файл: `alliance/tasks/views/tasks.py`

#### `manager_tasks(request)`

Страница менеджера для списка, создания и редактирования задач.

Поддерживает:

- открытие модального окна создания;
- предзаполнение назначенного работника или команды;
- редактирование задачи;
- валидацию формы;
- фильтрацию и пагинацию через `manager_tasks_queryset`;
- карту деталей задач для модального окна.

Шаблон: `templates/tasks/manager_tasks.html`.

#### `start_task(request, pk)`

Работник берет задачу в работу.

Условия:

- пользователь должен иметь доступ к задаче;
- задача должна быть в статусе `open`;
- после успешного действия статус меняется на `in_progress`.

#### `complete_task(request, pk)`

Работник закрывает задачу.

Логика:

- проверяет доступ;
- если задача уже закрыта, ничего не меняет;
- успех определяется по просрочке: просроченная задача считается проваленной;
- вызывает `apply_task_outcome`.

#### `manager_complete_task(request, pk)`

Менеджер закрывает задачу.

Особенности:

## 14. Бизнес-сервисы

### 14.1 Закрытие задач и рейтинг

Файл: `alliance/tasks/services/task_completion.py`

Главная функция:

```python
apply_task_outcome(task, success, completed_by=None)
```

Назначение:

- атомарно закрывает задачу;
- начисляет или снимает рейтинг;
- распределяет рейтинг между участниками;
- записывает `completed_by` и `completed_at`;
- запускает пересчет метрик.

Правила:

- если задача уже `completed` или `failed`, функция возвращает `None`;
- для индивидуальной задачи рейтинг получает назначенный работник;
- для командной задачи рейтинг делится между участниками команды;
- остаток от деления получает первый участник;
- рейтинг пользователя не опускается ниже нуля;
- успешная задача получает статус `completed`;
- неуспешная задача получает статус `failed`.

Функция `format_outcome_message(result)` формирует текст результата закрытия задачи.

### 14.2 Расчет рейтинга для отображения

Файл: `alliance/tasks/services/rating.py`

Функции:

- `split_rating_shares(amount, recipient_count)` - делит рейтинг между участниками;
- `get_rating_recipients(task)` - определяет получателей рейтинга;
- `rating_sign(success)` - возвращает `1` или `-1`;
- `rating_change_for_user(task, user)` - считает изменение рейтинга конкретного пользователя по закрытой задаче.

Этот модуль используется для страницы рейтинговой статистики работника.

### 14.3 Рекомендации работников и команд

Файл: `alliance/tasks/services/recommendations.py`

Назначение:

- оценить работника под тип задачи;
- оценить команду под тип задачи;
- вернуть отсортированный список рекомендаций.

#### Оценка работника

Функция:

```python
score_worker_for_task(user, task_type, task_rank=350)
```

Компоненты оценки:

- бонус за специализацию;
- соответствие hard skills;
- средний уровень soft skills;
- надежность;
- командность;
- бонус за текущий рейтинг;
- штраф за текущую нагрузку.

Результат:

- `score` от 0 до 100;
- `reasons` - причины рекомендации;
- `hard_fit`;
- `soft_avg`;
- `reliability`;
- `collaboration`;
- `specialization`.

#### Оценка команды

Функция:

```python
score_team_for_task(team, task_type, task_rank=350)
```

Компоненты оценки:

- совпадение доминирующего типа команды с типом задачи;
- средняя пригодность участников;
- синергия;
- совместимость;
- успешность прошлых командных задач.

#### Рекомендации

Функции:

- `recommend_workers_for_task(...)`;
- `recommend_teams_for_task(...)`;
- `score_worker_for_team(...)`;
- `recommend_workers_for_team(...)`.

### 14.4 Подбор состава команды

Файл: `alliance/tasks/services/team_composition.py`

Назначение:

Ключевые показатели:

## 22. Основные пользовательские сценарии

### 22.1 Регистрация работника

1. Пользователь открывает `/accounts/register/`.
2. Заполняет имя пользователя, email и пароль.
3. Если регистрация менеджера отключена, роль принудительно становится `worker`.
4. После успешной регистрации пользователь автоматически входит в систему.
5. Пользователь попадает на dashboard.

### 22.2 Регистрация менеджера

1. В `.env` задан `MANAGER_REGISTRATION_CODE`.
2. На форме регистрации доступны роль и код приглашения.
3. Пользователь выбирает роль `manager`.
4. Вводит код.
5. Если код совпадает, создается менеджер.

### 22.3 Создание задачи менеджером

1. Менеджер открывает `/manager/tasks/`.
2. Открывает форму создания.
3. Указывает название, описание, типы, рейтинг, срок.
4. Назначает либо работника, либо команду.
5. Backend валидирует форму.
6. Задача создается со статусом `open`.

### 22.4 Выполнение задачи работником

1. Работник видит задачу на своей странице.
2. Нажимает старт.
3. Статус задачи становится `in_progress`.
4. Работник закрывает задачу.
5. Если срок не просрочен, задача становится `completed`.
6. Если срок просрочен, задача становится `failed`.
7. Сервис закрытия меняет рейтинг и пересчитывает метрики.

### 22.5 Командная задача

1. Менеджер назначает задачу команде.
2. Участники команды видят задачу.
3. При закрытии рейтинг распределяется между участниками.
4. Пересчитываются метрики команды и участников.

### 22.6 Подбор исполнителя

1. Менеджер выбирает тип задачи.
2. Frontend вызывает `recommend-assignees`.
3. Backend считает score работников и команд.
4. Менеджер видит отсортированные рекомендации и причины.

### 22.7 Подбор состава команды

1. Менеджер создает или редактирует команду.
2. Выбирает целевые типы задач и/или навыки.
3. Frontend вызывает endpoint рекомендаций участников.
4. Backend оценивает кандидатов с учетом уже выбранного состава.
5. UI показывает score, причины и рекомендованных работников.

### 22.8 Учет рабочего времени

1. Работник включает таймер.
2. Создается `WorkSession`.
3. UI периодически отображает длительность.
4. Работник выключает таймер или выходит из системы.
5. Сессия закрывается.
6. Менеджер видит сводку рабочего времени.

## 25. Данные и миграции

Миграции:

- `accounts/migrations` описывает схему пользователей, навыков и рабочих сессий;
- `tasks/migrations` описывает схему задач, команд, типов задач и заметок менеджера.

База:

- локальная SQLite-база лежит в `alliance/db.sqlite3`;
- файл БД не является исходным кодом;
- для переноса проекта лучше использовать миграции и фикстуры, а не копирование БД.

## 26. Безопасность

Реализовано:

- стандартная Django-аутентификация;
- CSRF middleware;
- сессии Django;
- разграничение по ролям;
- декоратор `manager_required`;
- ограничения доступа к профилям работников;
- проверки доступа к задачам;
- код приглашения для регистрации менеджера.

Важно для production:

- заменить `SECRET_KEY`;
- отключить `DEBUG`;
- настроить `ALLOWED_HOSTS`;
- не хранить рабочую БД SQLite как production-хранилище;
- включить HTTPS;
- настроить secure cookies;
- добавить журналирование действий менеджера;
- добавить резервное копирование БД;
- проверить права доступа для всех POST endpoints.

## 27. Ограничения текущей реализации

Текущая версия проекта является учебным Django-монолитом.

Ограничения:

- нет REST API на DRF;
- нет OpenAPI/Swagger-документации;
- нет Docker-конфигурации;
- нет CI/CD;
- SQLite подходит для локальной разработки, но не для серьезной многопользовательской эксплуатации;
- рекомендации основаны на эвристических формулах, а не на ML-модели;
- часть UI-логики зависит от подготовленных JSON-словарей в шаблонах;
- нет отдельной системы уведомлений;
- нет календаря задач;
- нет экспорта отчетов;
- нет полноценного аудита действий пользователей.

## 30. Краткое резюме архитектуры

Alliance устроен как учебное, но достаточно содержательное Django-приложение. Центральная часть системы - модели `Task`, `Team`, `User`, `Skill`, `UserSkill` и `WorkSession`. Views обрабатывают пользовательские сценарии менеджера и работника, а основные правила вынесены в сервисы. Самые важные сервисные области: закрытие задач, рейтинг, рекомендации, подбор состава команды, рабочее время и пересчет метрик.

Проект уже имеет полезное разделение ответственности: данные находятся в моделях, HTTP-логика во views, сложные вычисления в `services`, UI-детали в шаблонах и static-файлах. Это хорошая основа для дальнейшего развития: перехода к PostgreSQL, добавления API, отчетов, уведомлений и production-инфраструктуры.
